# AIS Branch & Asset Operations — Work Order Process v1.0

สถานะเอกสาร: ข้อกำหนดกระบวนการตามการยืนยันล่าสุดของทาม  
ขอบเขต: ใช้เป็นเอกสารอ้างอิงของ MVP และการพัฒนาในเครื่อง ไม่ใช่หลักฐานว่า Production ได้รับ Migration หรือ Deploy แล้ว

## 1. เป้าหมายและบทบาท

ระบบใช้บันทึกงานเปลี่ยนเครื่องสแกนของสาขา ติดตามผลแยกตามเครื่อง และเก็บประวัติให้ตรวจสอบย้อนหลังได้

- **Admin** ดูแลทะเบียนและการนำเข้า เปิด/ยกเลิกใบงาน จัดการสิทธิ์ และทำขั้นตอน onsite ได้ครบ; หาก Admin เป็นผู้ปฏิบัติงาน ต้องให้ Admin อีกบัญชีลงนามตรวจรับ
- **Onsite Technician** มองเห็นใบงานทุกใบ บันทึกการเริ่มงาน ผลติดตั้ง และข้อมูลเครื่องเดิม/เครื่องใหม่
- การประชุมภายนอกเป็นผู้กำหนดว่าใครเดินทางไปสาขาใด ระบบไม่กำหนดทีมและไม่จำกัดการมองเห็นด้วยทีม
- ระบบบันทึกผู้ใช้ที่ส่งผลปฏิบัติงานจริงจากบัญชีที่ลงชื่อเข้าใช้ การอ่านเห็นทุกใบงานไม่ได้แปลว่าทุกคนเป็นผู้ปฏิบัติงานของทุกรายการ

## 2. ทะเบียนสาขาและ Scanner

1. Admin นำเข้าทะเบียนจากชีต `Detail1` ที่ผ่านการตรวจสอบแล้ว
2. ใช้ `comSN` เป็นตัวจับคู่เครื่อง ตัดช่องว่างหัวท้ายแต่คงตัวพิมพ์ และปฏิเสธ Batch ทั้งชุดเมื่อพบ key หาย/ซ้ำ หรือความสัมพันธ์ LocationCode กับสาขากำกวม
3. หนึ่งสาขามี Scanner ได้หลายเครื่อง จังหวัดเป็นข้อมูลของสาขา และใช้กรองสาขาก่อนเปิดใบงาน
4. `comSN` เดิมอัปเดตได้เฉพาะ master fields ที่อนุมัติ ช่องว่างจากไฟล์ใหม่ไม่ทับค่าที่มี ประวัติใบงานไม่ถูกเขียนทับ
5. LocationCode ใหม่ต้องให้ Admin ตรวจและสร้างสาขาก่อน Import จะผ่าน ส่วนข้อมูล Plan/TimeLine ไม่สร้างใบงานให้อัตโนมัติ
6. กรณีข้อมูลทะเบียนไม่ตรงกับที่พบหน้างาน ให้สร้างข้อยกเว้นเพื่อ Admin ตรวจ ไม่แก้ master โดยอัตโนมัติ

หมายเหตุ: มีรายงานข้อมูลต้นทางเดิมที่ระบุ 7 กลุ่ม LocationCode/ที่อยู่ซึ่งต้องตรวจแก้กับเจ้าของข้อมูลก่อนการนำเข้าหรือ Import รอบใหม่ สถานะการแก้ต้นทางต้องยืนยันจากไฟล์ฉบับที่จะใช้จริงก่อนดำเนินการ

## 3. การเปิดใบงาน

1. Admin เลือกจังหวัดเป็นตัวกรอง แล้วเลือก **หนึ่งสาขา**
2. Admin เลือก Scanner หนึ่งเครื่องหรือหลายเครื่องจากทะเบียนของสาขานั้น
3. ระบบปฏิเสธรายการว่าง, Scanner ที่ไม่อยู่ในสาขาที่เลือก, ID ซ้ำ, Scanner ที่มีใบงานยังไม่จบ และคำขอซ้ำจากการ retry
4. เมื่อบันทึกสำเร็จ ระบบสร้างใบงานหนึ่งใบที่มีรายการ Scanner หลายรายการได้ ใบงานเริ่มสถานะ `Open` และช่างทุกคนมองเห็นได้
5. การเปิดใบงานไม่ต้องสร้าง Campaign ก่อน และไม่มีการกำหนดทีม/ช่าง/วันนัดหมายเป็นเงื่อนไขบังคับ

ความสัมพันธ์หลัก:

```text
จังหวัด 1 ── หลายสาขา
สาขา 1 ── หลายใบงาน
ใบงาน 1 ── หลายรายการ Scanner
Scanner 1 ── ใบงานที่ยังไม่จบได้ไม่เกิน 1 ใบ
```

ประวัติใบงานที่จบหรือถูกยกเลิกยังคงเก็บไว้ Scanner จึงเปิดใบงานใหม่ได้เมื่อไม่มีใบงานที่ยังทำงานอยู่

## 4. การทำงานหน้างาน

1. ช่างทุกคนเปิดดูใบงานและเลือกงานที่ตนไปปฏิบัติจริงตามการประสานงาน
2. SN เป้าหมายและสาขามาจากทะเบียนที่ Admin นำเข้าและตรวจสอบแล้ว ผู้ปฏิบัติงานจึงเริ่มงานได้ทันที ไม่ต้องยืนยัน SN/สาขาซ้ำ
3. เมื่อเริ่มรายการเครื่อง ระบบเปลี่ยนรายการนั้นเป็น `In Progress` และบันทึกบัญชีผู้เริ่ม/เวลา
4. เมื่อเปลี่ยนเครื่อง ผู้ปฏิบัติงานบันทึก Serial เดิม/ใหม่ ผลการติดตั้ง สถานะเครื่องเดิม และหมายเหตุเมื่อจำเป็น
5. ผู้ปฏิบัติงานแนบรูป SN เดิม, SN ใหม่, เครื่องเดิม, เครื่องใหม่ และลายเซ็นผู้ปฏิบัติงานกับผู้ใช้ Scanner จากนั้นส่งให้ Admin อีกบัญชีตรวจรับ
6. Admin ทำขั้นตอน onsite แทนช่างได้ทั้งหมดและส่งปิดงานได้ แต่การตรวจรับต้องลงชื่อโดย Admin อีกบัญชี ผู้ที่ปฏิบัติงานรายการนั้นลงชื่อรับงานของตนเองไม่ได้
7. หลัง Admin รับผ่านเท่านั้น ระบบจึงปรับ Serial ในทะเบียนและปิดรายการเป็น `Completed`/ส่งมอบ
8. ระบบบันทึกผู้ปฏิบัติงานและเวลาอัตโนมัติจากบัญชีที่ลงชื่อเข้าใช้ ไม่ใช้ชื่อที่กรอกจาก client เป็นตัวตัดสินผู้ทำงาน
9. เครื่องเดิมเป็นผลการปฏิบัติงาน ไม่สร้างรายการคลังหรือ Stock โดยอัตโนมัติ

ระบบใช้ version check/การตรวจสถานะก่อนบันทึก เพื่อป้องกันผลจากการแก้รายการเดียวกันพร้อมกัน และบันทึก actor ของผู้ส่งข้อมูลจาก session ที่ยืนยันตัวตน ไม่เชื่อ actor ที่ส่งมาจาก client

## 5. กรณีไม่พบเครื่องและการตรวจข้อยกเว้น

ทะเบียนที่ยืนยันแล้วเป็นข้อมูลอ้างอิงปกติ จึงไม่ต้องมีขั้นตอนให้ช่างยืนยันซ้ำ ข้อยกเว้นเริ่มเมื่อหน้างานไม่ตรงกับ SN ในใบงาน:

1. **ไม่พบ SN ตามใบงาน แต่พบ Scanner อีกเครื่อง** — ผู้ปฏิบัติงานบันทึก SN/รุ่นที่อ่านได้และเหตุผล ถ่ายรูปฉลาก SN กับตัวเครื่อง และให้ผู้ปฏิบัติงาน/ผู้ใช้ Scanner ลงชื่อ รายการนั้นเป็น `Pending`; ระบบไม่เขียนทะเบียน
2. **ไม่พบทั้งเครื่องตามใบงานและไม่พบ Scanner เครื่องอื่น** — ผู้ปฏิบัติงานบันทึกเหตุผล ถ่ายรูปบริเวณที่ตรวจค้น (ถ้าทำได้) และส่งให้ Admin ตรวจเป็น `Pending`; ไม่มี SN ใหม่ให้เพิ่ม
3. **ไม่พบเครื่องชำรุดหรือผลอื่นที่ยังปิดงานปกติไม่ได้** — ผู้ปฏิบัติงานบันทึกผล เหตุผล และหลักฐานที่เกี่ยวข้อง แล้วพักเฉพาะรายการนั้นเป็น `Pending` เพื่อให้ Admin ตรวจ
4. Admin ตรวจสาขา SN เหตุผล รูป และลายเซ็นก่อนลงลายเซ็น Admin อีกบัญชีเพื่อบันทึกผลพิจารณา ผู้ที่ปฏิบัติงานรายการนั้นห้ามตรวจรับรายการเดียวกัน
5. เฉพาะกรณีพบเครื่องอื่นและตรวจแล้วว่า SN **ยังไม่มีในทะเบียนทุกสาขา** Admin จึงอนุมัติเพิ่ม SN นั้นเข้าทะเบียนสาขาของใบงาน การเพิ่มทะเบียนและ Audit เกิดพร้อมกันใน Transaction
6. หาก SN อยู่ในสาขาเดียวกันอยู่แล้ว ระบบไม่สร้างซ้ำ; หากอยู่สาขาอื่น ระบบปฏิเสธ ไม่ย้ายและไม่แก้ทะเบียนเดิมอัตโนมัติ ให้ Admin ตรวจและแก้ข้อมูลหลักผ่านการทำรายการที่มี Audit ก่อน
7. การตรวจข้อยกเว้นจะปิดเป็น `exception_resolved` และ **ไม่ถือว่าเปลี่ยนหรือส่งมอบเครื่องแล้ว** หาก SN ที่พบต้องเปลี่ยนจริง Admin เปิดรายการงานใหม่โดยใช้ SN ที่ตรวจสอบ/เพิ่มทะเบียนแล้ว เพื่อรักษาประวัติของ SN เป้าหมายเดิม
8. หากต้องเข้าหน้างานซ้ำ ให้ Admin ยกเลิกรายการเดิมพร้อมเหตุผล แล้วเปิดรายการใหม่; ประวัติเดิมไม่ถูกลบ
9. ห้ามกรอก SN สมมติหรือเพิ่ม SN ที่หน้างานไม่ได้พบจริง

ข้อยกเว้นเป็นราย Scanner ไม่หยุดเครื่องอื่นในใบงานเดียวกัน ช่างจึงรายงานเครื่องที่หาไม่พบได้หลายสิบเครื่องในคราวเดียวโดยแต่ละรายการยังแยกหลักฐานและผู้ปฏิบัติงาน Admin ตรวจแต่ละรายการภายหลังได้ การเพิ่ม SN พบใหม่ไม่ใช่ระบบ Stock และไม่สร้างใบงานเปลี่ยนเครื่องให้อัตโนมัติ

## 6. สถานะและการปิดงาน

สถานะราย Scanner:

```text
Open → In Progress → Pending (รอ Admin ตรวจรับ) → Completed (ส่งมอบ)
          ↘ Pending (ข้อยกเว้น) → exception_resolved (ตรวจแล้ว ไม่ใช่ส่งมอบ)
Open / In Progress / Pending → Cancelled (Admin + เหตุผล)
```

ข้อกำหนดการเปลี่ยนสถานะ:

- `Open` — Admin เปิดใบงานแล้ว แต่ยังไม่มีช่างเริ่มรายการ
- `In Progress` — มีผู้ปฏิบัติงานเริ่มรายการแล้ว
- `Pending` — มีเหตุผลที่ต้องพักรายการ; ไม่หยุด Scanner อื่นในใบงาน
- `Completed` — Admin ตรวจรับพร้อมลายเซ็นแล้ว ระบบจึงเปลี่ยน Serial ในทะเบียนและส่งมอบงาน
- `exception_resolved` — Admin ตรวจข้อยกเว้นแล้ว แต่ไม่มีการเปลี่ยนเครื่องตามรายการเดิม
- `Cancelled` — Admin ยกเลิกรายการพร้อมเหตุผล

สถานะใบงานเป็นค่ารวมจากรายการเครื่อง:

- `Cancelled` เมื่อทุกรายการถูกยกเลิก
- `Completed` เมื่อทุกรายการเป็น Completed หรือ Cancelled และมีอย่างน้อยหนึ่งรายการ Completed
- `In Progress` เมื่อยังมีรายการที่กำลังทำงาน
- `Pending` เมื่อมีรายการ Pending และไม่มีรายการที่กำลังทำงานหรือ Open
- `exception_resolved` เมื่อรายการที่เหลือทั้งหมดปิดแล้วแต่มีข้อยกเว้นที่ Admin ตรวจแล้วและไม่มีรายการที่กำลังทำงาน
- `Open` ในกรณีที่ยังไม่มีรายการเริ่มทำงานหรือพักค้าง

รายการที่ Admin ตรวจรับตามปกติจึงเป็น `Completed`; รายการข้อยกเว้นที่ตรวจแล้วแสดงแยกและไม่นับเป็นงานส่งมอบ ส่วนการเพิ่ม SN ใหม่ทำได้เฉพาะเมื่อพบเครื่องจริงและ Admin อนุมัติ

## 7. สิทธิ์และข้อมูลส่วนบุคคล

- ผู้ใช้จริงมีเพียง Admin และ Onsite Technician; ไม่มี Planner, Data Manager หรือ Viewer เป็นบทบาทปฏิบัติงาน
- ทุก RPC/การอ่านและการเขียนต้องตรวจบัญชีที่ active และ role ฝั่งฐานข้อมูล; การซ่อนปุ่มใน UI ไม่ใช่การควบคุมสิทธิ์
- Raw tables อยู่ใน schema ภายในและไม่ให้ browser อ่านโดยตรง ใช้ RPC ที่ตรวจ authorization และให้สิทธิ์ execute เท่าที่จำเป็น
- `empMail` ไม่อยู่ในทะเบียนและไม่แสดงทุก role
- รูปและลายเซ็นเป็นหลักฐานบังคับตามขั้นตอน: งานเปลี่ยนปกติต้องมีรูป SN/ตัวเครื่องเดิมและใหม่ ลายเซ็นช่าง ลายเซ็นผู้ใช้ Scanner และลายเซ็น Admin ผู้ตรวจรับ
- กรณีพบเครื่องอื่นต้องมีรูป SN/ตัวเครื่องที่พบ ลายเซ็นช่างและผู้ใช้ Scanner ก่อนส่ง Pending; Admin ลงลายเซ็นเมื่อตรวจผล
- กรณีไม่พบทั้งสองเครื่องให้ถ่ายรูปบริเวณที่ตรวจค้นได้และลงลายเซ็นผู้เกี่ยวข้อง; Admin บันทึกผลตรวจข้อยกเว้น
- หลักฐานดูได้ในรายละเอียดใบงานทุกสถานะ และข้อมูลผู้ลงนาม/เวลาอ้างอิงจากบัญชีและเวลาเซิร์ฟเวอร์
- ผู้ปฏิบัติงานและเวลาบันทึกมาจากบัญชีที่ยืนยันตัวตนและเวลาเซิร์ฟเวอร์

## 8. การเก็บข้อมูลเดิมและข้อจำกัดการปล่อยระบบ

- Migration ใหม่ต้องรักษา `replacement_tasks`, `field_visits`, audit และหลักฐานเดิม โดยไม่รวมประวัติที่เกิดคนละงานย้อนหลังเข้าด้วยกัน
- Campaign และ task เก่าต้องคงไว้ให้อ่านประวัติได้ แต่ไม่ใช้สร้างหรือแก้ใบงานใหม่; รายการที่ถูกเลือกใน Campaign เก่าแต่ยังไม่มี task ห้ามสร้างเป็นใบงาน active อัตโนมัติ
- การพัฒนารอบนี้ทำใน workspace เท่านั้น จนกว่าจะตรวจ migration/backfill, RLS, regression tests, backup/restore และอนุมัติการปล่อยแยกต่างหาก
- Stack ที่อนุมัติไว้คือ React/TypeScript/Vite, Supabase Free (Singapore) และ Cloudflare Free โดยเป้าหมายค่าใช้จ่าย 0 บาทและยอมรับข้อจำกัด Free tier
- เป้าหมายพัฒนา 3 วันเป็นกรอบ MVP ชั่วคราว ไม่ใช่การรับรองว่า Production พร้อมใช้งานภายในเวลานั้น

## 9. เกณฑ์รับงานสำหรับ Process ใหม่

- Admin เปิดใบงานหนึ่งสาขาที่มี Scanner หลายเครื่องได้ และปฏิเสธเครื่องข้ามสาขา/เครื่องที่ยังมีใบงาน active
- มีบทบาทใช้งานสองแบบคือ Admin และ Onsite Technician; ช่างทุกคนอ่านใบงานได้ทุกใบ และไม่มี team gate
- เริ่มงานจาก SN ที่ยืนยันในทะเบียนได้โดยไม่ถามยืนยันซ้ำ
- กรณี SN ไม่ตรง/ไม่พบ ต้องมีเหตุผล หลักฐาน และลายเซ็นที่จำเป็น แล้วเปลี่ยนเฉพาะรายการนั้นเป็น Pending; ทะเบียนไม่เปลี่ยนก่อน Admin ตรวจ
- เพิ่ม SN ที่พบใหม่ได้เฉพาะหลัง Admin ตรวจว่าไม่ซ้ำทุกสาขา; การเพิ่มและ Audit เกิดใน Transaction เดียว และ SN ข้ามสาขาถูกปฏิเสธ
- งานปกติต้องมี Serial ใหม่ ผลติดตั้ง/ทดสอบ รูป และลายเซ็นช่าง/ผู้ใช้ Scanner ครบก่อนส่งให้ Admin อีกบัญชีลงลายเซ็นรับผ่าน; จากนั้นระบบจึงปรับทะเบียนและส่งมอบ
- Admin ตรวจข้อยกเว้นและปิดเป็น `exception_resolved` ซึ่งต้องไม่แสดงว่า Completed/ส่งมอบ; หากต้องเปลี่ยน SN ที่พบ ให้เปิดรายการใหม่ด้วย SN นั้นหลังตรวจทะเบียน
- ระบบป้องกันการปิดงานไม่ครบและการส่งคำขอซ้ำ พร้อมบันทึก actor/time
- Import ปฏิเสธ Batch ผิดทั้งชุด รักษาประวัติงานเมื่อ update master และไม่เพิ่ม SN ใหม่จาก exception ก่อน Admin อนุมัติ
- ทดสอบหน้าจอและการนำทางบนโทรศัพท์ รวมถึงการเปิดรายละเอียดใบงานที่มีหลาย Scanner
- การทดสอบ Production/การ Deploy ทำได้หลังได้รับการอนุมัติแยก และต้องตรวจ backup/restore กับสิทธิ์ฐานข้อมูลก่อน
